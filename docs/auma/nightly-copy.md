# Her nightly cloud copy

This reference is for Auma and the owner. SOURCE describes the checked-in implementation. RAN describes local tests using in-memory storage. NOT VERIFIED identifies behavior that has not been observed on Cloudflare.

## What is kept

SOURCE — Each run copies every stored key from HEAD, MIRROR, VoiceBridge and Witness, except three HEAD rows, one field, and the MIRROR rows the secret-path rule hides, named below. It does not choose files by name or depend on a subsystem's data format. The copy includes conversation indexes, ordered piece lists, conversation open ends, messages between people, the turn journal, voice memory, witness records, leases, lockouts and budgets. It does **not** include the owner binding at `aumlok:v1` any more; the recovery impact is stated below.

SOURCE — Three HEAD keys stay out: `aumlok:signin:v1` holds live sign-in sessions and used sign-in challenges; `aumlok:devices:pending:v1` holds pending device-enrolment codes and challenges; `aumlok:v1` is the owner binding, which on the unseparated pepper scheme carries the whole pepper and the wrapped root, so a copied row would remove the Touch ID and the attempt limit from guessing the seven recovery words, which the holder of a set could then do offline. No key is excluded from the other three objects by exact name; MIRROR withholds rows by the same secret-path rule every other MIRROR reader uses, and every conflict row. The rule reads the path where the mirror keeps it. A stored MIRROR key is the SHA-256 of the path (`mirrorDigest`), never the path, so an entry row is judged by `value.path`, a reset row by its value (the path itself), and a chunk row — which carries no path at all — by reading the entry for its digest: a chunk whose entry is missing or has no string path is withheld, because the only alternative is to copy bytes whose path nothing in storage still names; a read that throws fails the page instead, so a storage fault is never counted as a hidden path. Whether the rule actually reads the value is recorded in the manifest (`withheldReads: "value"`), and a set whose manifest has no such marker was copied by the earlier rule, which read the key and matched nothing on real data: its withheld count is not evidence about hidden paths. Hidden-path rows and conflict rows are counted separately (`withheldHidden`, `withheldConflict`) and only the counts are recorded, never a path or a digest. These are exact names, not a broad filter for anything that resembles a secret. The copier names excluded keys in the manifest but never inspects or encodes their values. Cloudflare's key-value `list()` returns values along with keys; there is no keys-only list in this implementation, so the platform still returns those values to the object during listing.

SOURCE — One copied value is redacted: `messages:v1` keeps its conversations, its turns and the public identity fields, while `identity.secretKey` (the Nostr signing key) is replaced by the fixed marker `[nightly-copy:redacted]`. The manifest's `redacted` list names the key once, on the page that carries its row, and never the field value, and `/_host/nightly` reports a redacted count beside the excluded count. A messages state that carries no identity is not labelled redacted: only an actual replacement is named. A restored value that carries the marker is refused as `MESSAGES_STATE_CORRUPT` by every validated path, provisioning included: strip or replace `identity` before writing it back.

SOURCE — Ordinary JSON values retain their meaning. Byte arrays, buffers, dates and undefined members have explicit tags; literal dollar-prefixed keys are escaped. Negative zero also has a tag. Values the encoder cannot preserve, including Maps, Sets, BigInts, functions, non-finite numbers, cycles, shared object identity, sparse arrays and custom object types, are named as unreadable. Other rows and objects continue. An unreadable row makes the set incomplete; it is never silently replaced or dropped from the accounting.

## Where and when

SOURCE — Each object is read under the name its own callers use: HEAD, MIRROR and Witness as `node-main-v1`, VoiceBridge as `x61-voice-bridge-v1` (`OBJECT_IDS`; a test pins them against the callers' source). A wrong name would address a new, empty object and report a complete copy of nothing.

SOURCE — The pages rest in `ARCHIVE_BUCKET` under `nightly/<UTC-start-time>/<object>/00000.json`, followed by `manifest.json`. Object folders are `HEAD`, `MIRROR`, `VOICE_BRIDGE` and `WITNESS`, in that copy order. A start time looks like `2026-11-18T19-17-00Z`. Each page and the manifest are hashed over the exact UTF-8 text written. The manifest includes page counts, row counts, bytes, omitted and unreadable names, the withheld counts with the MIRROR rule version and how the path was read, alarms, build identifiers and closed failure codes. A page must carry both split counts and their sum must equal its total, so a page from code that judged the key fails its object instead of publishing a set. Page reads are bounded to 1,000 scanned keys and roughly 4 MiB of encoded rows; a larger row gets its own page. Storage lists use smaller batches within a page.

SOURCE — The existing hourly schedule calls the witness first and then the copy; failures are isolated. Exactly `NIGHTLY_COPY = "on"` enables the copy, and that is the shipped configuration. `"off"`, a missing value or any other value disables it. The nightly window starts at 19:00 UTC, which is 03:00 for the owner in UTC+8. With the current minute-17 cron, the first usual attempt is 03:17. If no complete set exists, the next scheduled call can make an initial copy before that hour.

SOURCE — `nightly/STATE.json` reserves at most three attempts in each window beginning at 19:00 UTC. An interrupted attempt counts. A running reservation blocks another for one hour; a later scheduled call can spend the next attempt. Conditional R2 writes prevent two callers from claiming the same reservation. Once tonight's complete set is published, another call tonight writes nothing. An existing set name is never overwritten.

SOURCE — Only a complete set with a successful vault inventory updates `nightly/LATEST.json`, which holds its set name, manifest SHA-256 and finish time. A failed object does not stop the other objects. An incomplete set still gets a manifest if the bucket accepts it. A set without a manifest is unfinished and never becomes LATEST. A failed page, manifest or pointer write leaves a closed code in the attempt state when that state write succeeds.

## Reading the status

SOURCE — From the signed-in owner's page on the same origin, request `GET /_host/nightly` without a query. It has the archive status read's owner and same-origin requirements. It returns the newest manifest's counts, including incomplete sets: rows, bytes, pages, exclusion, redaction, withheld and unreadable counts, with the withheld total split into hidden-path and conflict counts and the marker saying how the path was read (a manifest written before redaction, the split or the MIRROR rule existed reports each missing count as `null`, never as zero), change observations, bookmark presence and vault totals. It also gives the attempt state, closed object failure codes and the newest 30 manifest-bearing sets with their manifest SHA-256 values. It returns no row contents, stored key lists or bookmark values. `latestCompleteSet` identifies the set selected by LATEST. `/api/health` has `lastNightly` for that last complete set, or null when it cannot be read and verified.

SOURCE — `changedDuring: true` means the first page differed when read again. `false` means equal before/after bookmarks or a matching single-page reread; it is not a promise that the four objects share one instant. `null` means there is insufficient evidence, including a multi-page copy whose first page agrees but whose bookmarks are unavailable or different (whether a bookmark moves with time alone is NOT VERIFIED, so two different bookmarks never say "changed"). The four objects are copied at different times, and page reads are not one atomic snapshot. Completeness says every page was written and every included value was representable, not that the world stood still.

SOURCE — If SQLite's `getCurrentBookmark()` is available, the internal read records a bookmark before the first page and after the last. If it is absent, the values are null with reason `unavailable`; a failed call has reason `failed`. The platform's stated SQLite history window is 30 days. These bookmarks identify restore points in that history; this lane builds no way to restore from them and does not change an alarm.

## What this cannot recover

SOURCE — Vault pieces already live in the same R2 bucket under `w/node-main-v1/blob/`. The copy lists them in pages, counts their bytes and hashes the sorted `key size` lines, each ending with a newline. It does not read, duplicate or verify the pieces' contents. This is not an independent copy of the bucket, nor an inventory of its other prefixes. Anything a browser has not sent is absent. Auma's own browser signing key never leaves the browser and is not in this copy. Worker environment secrets and in-memory socket state are not Durable Object key-value rows and are not copied.

SOURCE — **Recovery impact of the exclusions.** A completed set is no longer enough to restore Auma's owner binding. Restoring HEAD without `aumlok:v1` leaves the new object unbound: the passkey enrolment, the recovery commitment and the wrapped root must come from the owner's own recovery material. This lane does not copy it, but the bucket is not proof that it is absent: the owner archive-export route writes the whole `aumlok:v1` row under `snapshots/` in this same bucket when it runs. A read of that prefixZ found 0 objects (R2 list), so no export has run; had one run, the row would be there. A restored `messages:v1` carries the marker, not the key; its signed turns will not pass `validateState` (a non-hex `secretKey` fails `validIdentity`, and signed turns must match `state.identity.pubkey`), so messages restore requires a fresh identity and old signed turns cannot be re-validated as they stand. The transcript itself remains readable as data. A restore must strip or replace `identity` before writing the value back: the marker fails `validIdentity`, and `validateState` reports the whole stored value as corrupt (`messages-store.mjs:582`), not only the signing part.

SOURCE — **Existing sets are not fixed by this change.** Sets written before it still contain the legacy owner row and the plaintext Nostr key, so they still remove the Touch ID and the attempt limit from guessing the seven words. This change protects future sets only. Any set made on real data before it may still hold hidden files' paths and their bytes, and nothing here removes them; deleting those sets is owner work, on his list beside the old owner rows. The unseparated pepper scheme is still live: `AUMLOK_PEPPER_SECRET` is not set, so separation is unreachable until the owner writes that Worker secret and runs the migration. Retiring a root needs a client-minted fresh root (the refresh ceremony re-wraps, it does not mint) plus deletion of the old sets, both of which are owner actions.

SOURCE — Nothing is deleted by this feature. Older sets, incomplete sets and orphan pages remain. Storage grows by approximately one full encoded KV copy plus manifests each successful night, with additional partial data from failures. STATE and LATEST are small replaceable control records. No retention limit or live restore is built.

## Evidence and limits

RAN — `node --test deploy/cloudflare/src/__tests__/nightly-copy.test.mjs` exercises the real four Durable Object classes over fakes. It seeds HEAD and MIRROR through the recovery fixture's bootstrap sequence, adds conversation, message, journal, voice and witness rows, copies them, checks hashes, decodes every row into fresh in-memory stores and compares each store key by key. It also exercises 30,000 keys, UTF-8 ordering, a multi-page real-object copy, exclusions, unreadable values, mutation between pages, failure isolation, retries, overlapping reservations, owner status and public-route rejection. A synthetic owner row and a synthetic signing key must both be absent from every page and the manifest while the rest of the messages value still copies and the set still completes, and a redaction that throws must fail the page rather than copy the unreplaced value. A malformed messages shape must fail the page too. The MIRROR fixtures are seeded through the mirror's own `mirrorDigest`, with the path in the value exactly as the mirror stores it: a hidden file's entry, chunk and reset row must be withheld and counted apart from a conflict row while an ordinary file's entry and chunk copy; a chunk whose entry is missing or carries no string path must be withheld, and a read that throws must fail the page instead of counting anything as hidden; a `mirror:v2:conflict-chunk:` row must be withheld with the other conflict rows; the hidden chunk's base64 bytes carry a long marker, so the hidden path, its digest, the marker and its base64 form must appear in no written object. A page missing either split count, or whose split does not sum to its total, must fail the object. The rebuild drill's provisioned identity must come back unable to sign. The rebuild helper exists only in the test file.

NOT VERIFIED — This lane does not exercise the bookmark API or its 30-day history on Cloudflare, real R2 list paging or conditional writes, scheduled execution, CPU time and memory on a real home, or any installed program. The live MIRROR hidden-row count is not measured either: no route enumerates raw MIRROR storage, so the first real measurement is the first complete set's manifest written after this change lands. Neither is the extra cost the rule adds — one entry read per file on each page that has chunks, not one per chunk, because consecutive chunk keys share a digest and the verdict is reused within a page — measured on a real home. An operator must deploy and observe those behaviors. No live restore or bookmark restore exists to verify.
