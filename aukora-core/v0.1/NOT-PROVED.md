# What the release trusts

**A successful install proves a property of the carried Lean model.** The outgoing core checks the file digest, the matching model commitment, the install grant and a proof of `Aukora.Release.Lawful` for the last carried definition. The custom section is a claim by the file's producer. The release has no proof that Wasm instructions, the C adapter, the next file's own checker or host execution implement that model. The fixed-owner example was compiled from the release sources and exercised as a fresh instance. This supplies evidence for that file. [Gate](Gate.lean) · [Section parser](ModelSection.lean) · [Source-built example](FixedGenesis.lean)

**Nobody can change this gate's pinned law set from inside it.** The goal name and base declaration environment are compiled into its Wasm. Every proof check starts from that base. The byte API exposes no operation for replacing it. A change to the law set requires building different software outside this gate. Once a host executes another file, the outgoing gate cannot establish that file's own behavior without a model-to-bytes result. ### The two checkers

The bundled Lean 4.19.0 kernel checked the release proof from source. `#print axioms newest_lawful` reports propositional extensionality, classical choice and quotient soundness. The independent in-Wasm check uses the vendored Lean4Lean type checker, a binary expression parser and a serialized environment. It type-checks the carried definitions and proof. It takes **531 earlier theorem statements and 21 opaque declarations** by type, alongside one explicit axiom, `Classical.choice`. Trusted statements include the component lemmas used to assemble the release proof. There are 3,630 entries in total. The full release theorem, the candidate's assembled theorem and the carried definitions are excluded. The legacy context ingredients support the wrong-theorem control. The old proof succeeds on its original proposition and fails on the release target. [Every declaration, its trust class and serialized size](trust/checker-declarations.tsv) · [Exporter](tools/Export.lean) · [Native checker tests](tests/Check.lean)

The declaration language accepts **1–64 fresh safe monomorphic, nonrecursive definitions** with names under `R9Candidate`. A body may use pinned constants and earlier definitions in its carrier. Each type must have a sort, each body must have its declared type, and the final definition must be a valid argument to the pinned proposition. The format supplies no constructors for adding axioms, unproved lemmas or reduction rules. The package imposes one combined 1 MiB limit on the model and proof. General Lean source, recursive declarations, new inductive types and arbitrary independently implemented state schemas are outside this format. The release model uses the common public state schema. The serializers, parsers, Lean4Lean implementation and agreement with the native kernel have no end-to-end correctness theorem. ### Signatures, evidence and hosts

- Every signature law uses the verdict of the concrete Lean Ed25519 and ML-DSA-65 verifiers on its stated key and message. Key custody, entropy, implementation correctness, unforgeability and side-channel resistance are assumptions. A true verifier result identifies the signing key only under those assumptions. The input carries raw public keys. The public fixtures include RFC test material and detached signed messages. [Crypto sources](Crypto) · [Grant provenance](Proofs/GrantOrigin.lean)
- SHA-256 determines ledger heads, candidate digests and commitments. SHA-512 and SHAKE also enter the signature implementations. Vector comparisons test selected inputs. Collision resistance, preimage resistance and a proof of conformance to the cryptographic specifications remain outside the law set. Inferring equality of two files from their shared digest needs the explicit equality premise in L8. [Law statements and premises](PROVED.md)
- The host supplies assessments, bundle digests, destination reports and the read-authentication flag. A stamp retains opaque beacon and receipt data at the claimed current head. The machine establishes their history and bytes. External truth, time, delivery, independent beacon verification, the quality of an assessment and human intent require external evidence. A confirmed outcome records what was reported. [Wire fields](WIRE.md) · [Stamps](Proofs/Stamp.lean)
- Staging and grant consumption change the ledger's installed digest. The host resolves and instantiates the selected file. The section reader checks framing and commitment, while the Wasm engine validates instructions. Host persistence, migration of an existing live host's state into the next instance, crash recovery, concurrent host access, production activation and availability under arbitrary resource pressure have no proof or production test here. [Lab host and fresh-instance test](tests/gate.mjs)
- The Wasm input adapter, reachable-C extraction, compiler, linker, native and Wasm runtimes, watchdog, Node/V8, OpenSSL and operating system are trusted tools. The artifacts have no imports. The corpus compares submitted bytes, verdicts and complete heads over finitely many sessions. The corpus and SHA pins do not establish correctness for every input, toolchain or platform. The release scripts target the bundled Apple Silicon toolchains on this lab machine. [Adapter](Interface.c) · [Linker driver](tools/link.py) · [Conformance corpus](vectors)
