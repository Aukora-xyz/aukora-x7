A. Judge lineage
WASM  node v0.3/tests/judge12.mjs (r12/judge-wasm.log)
  R11's foundation identity was a statement by the running program about
  itself. The judge includes lean4lean, the reached Lean/Wasm runtime and
  parser code, the type/entailment goal constructors, and the actual pinned
  declaration snapshot installed by Context.c. Build-time code expands the
  aggregate proofs; the checker trusts a foundation which includes component
  theorem statements. Host/runtime/kernel/crypto correctness remain assumptions.
  Option (a) alone would authenticate a named custom environment copy. A
  candidate could compile against different data. Option (b) requires the
  host to instantiate the named separate judge and use its decision on the exact
  target. We chose (c): fix the entire executable prefix after export stripping.
  The outgoing core reads the actual staged bytes. It compares the embedded
  pin and hashes the normalized prefix, including the complete code and
  initialized data sections; only length-framed custom sections can follow. A conforming host must also
  validate UTF-8 names and the entire module. It
  therefore also names the compiled runtime, checker and goal constructor.
  See v0.3/tools/JudgePin.h and tools/seal-judge.py. Main costs are staging
  the executable, one hash per changed staging area, and forbidding even a
  legitimate change to any executable bytes. Extra predicates travel in metadata
  against the fixed foundation. The compiled handler executes. Equivalence of a
  submitted model and that compiled transition remains unproved.
  Probe: changed one real, equal-length serialized definition in the actual
  initializer data. The named comparison control formerly required the standard
  genesis and its new body permitted any genesis. Export12.LineageControl's
  strictness theorem was checked. This control is outside the security root.
  Equal file size and valid Wasm in both cases; only the outgoing file ran.
  A matching grant/target for EACH staged file, identical carried model and
  proof. Altered file: 11 before checking. Identical judge: comparison passed,
  witness mask 1 (satisfaction only), submitted transition witness refused. This isolates
  executable lineage without claiming admission of an impossible successor.
  Strongest conclusion: subject to SHA-256 collision resistance, the
  accepted prefix must contain the same executable bytes, including the real
  declaration data. The byte comparison cannot prove that any code correctly
  implements or executes the mathematical judge, or that a host actually
  selects these bytes and continues their ledger.

  Full/lite initially 223/147 pages. Both declare 4,096 64-KiB pages max
  (256 MiB): space for the 8-MiB stack, foundation, at most 16 MiB of staged
  data, limited record, plus transient parsing/verification. This is an

  release with room for metadata. Model + proof share an independent 1 MiB.
  One input may be 1,179,774 bytes; assembly failures consume the rejected
  submission but preserve the prior machine. Over-limit feeds keep all prior
  staged bytes and the ability to finish or reset staging. A validated call

  exact stored bytes. New instances have separate genesis; no checkpoint or
  continuity beyond a terminal record is claimed. Tests exercised below,
  at and over limits, preserved the prior file after rejection and used a
  harmless engine probe carrying each release's exact private memory section.
  On each profile the very same valid signed clear succeeded in the instance
  with room and was refused unchanged by the instance at capacity.
  finite_session_excludes_H5 demonstrates this conflict in the model. A
  refused nonempty feed in an open state separately contradicts the exact
  L1 feed promise (open_feed_refusal). The model states the finite wrapper
  explicitly, and Wasm enforces the engineering quota.
  Replay, staging and resource limits apply to finite sessions. Physical
  H5 cannot be unconditional with this record policy. The Lean Option law
  has only accept/refuse outcomes. The implementation preflights quota
  before allocations for a submission. Growth failure can still trap during
  engine instantiation, allocations in valid small calls, cryptography, hashes,
  decoding, proof checking or stack use. Physical no-trap/OOM was not proved.
